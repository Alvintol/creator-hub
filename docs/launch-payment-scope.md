## Cloudflare boundary

Hosting the Vite site and domain on Cloudflare does **not** remove any of the payment, Connect, refund, dispute, policy, or audit work. Stripe still owns charges on connected accounts, Supabase still holds project/payment state, and an HTTPS API endpoint still must receive and verify **Connect** events. Cloudflare Pages static hosting does not run `api/server.js`. For launch, either host the existing Express API separately and route `/api/*` to it, or port and test the API on Workers/Pages Functions. Configure production API origin, CORS, redirects, secrets, and Stripe's Connect webhook endpoint for the chosen deployment. Preserve the raw webhook body for signature verification. An API runtime move changes deployment and integration tests, not the business rules below. See [Cloudflare Pages Functions](https://developers.cloudflare.com/pages/functions/) and [Stripe webhooks](https://docs.stripe.com/webhooks).

## Recommended narrow launch contract

| Area | Proposed rule | Current evidence / change needed |
| --- | --- | --- |
| Seller and transaction geography | Pilot with **Canada-based connected creators and CAD payments**. Gate onboarding and agreement creation at the API/database, not only in forms. Limit paid buyers to Canada pending a documented cross-border tax/consumer review; free assets may be visible more broadly subject to content rules. Expansion to the US/other countries and USD is a separate release. This is a recommendation pending owner approval. | `CreatorPayoutSettings.tsx` takes arbitrary two-letter country/three-letter currency; `api/server.js` validates format only and defaults embedded onboarding to CA. Agreement/payment schema accepts arbitrary three-letter codes; fee bridge always multiplies by 100 and uses fixed 100/150 minor-unit minimums. Draft fee page mentions CAD and USD. |
| Paid catalog | Custom digital commissions/services through accepted request, agreement and explicit payment schedule: starting payment, milestone, change order, final balance. One payment obligation per schedule item; no direct purchase of paid instant downloads. No subscription, ads, escrow, automatic release or standalone `one_time` checkout at launch. | Existing schedule bridge supports the four payment timings; `one_time` is schema/API vocabulary without a workflow. README roadmap describes future features. |
| Free catalog | A free digital asset may be a public download or external link with **no** request payment, Checkout, buyer fee, creator fee or tip. Apply creator/content moderation and link/file safety checks. Decide whether approved creators without Connect may publish free items; recommendation: yes. | `20260919_115_add_free_listings.sql` and listing UI implement direct public access, but `20260622_107_require_payment_account_for_active_listings.sql` still requires ready Stripe for *every* active published listing; UI guard is also not free-aware. Support playbooks predate free listings. |
| Fee calculation | For each successfully collected CAD base installment `B` in cents: buyer fee `max(ceil(B × 0.05), 100)`; creator fee `max(ceil(B × 0.05), 150)`. Charge buyer `B + buyer fee + tip + support + separately disclosed tax`; application fee `buyer fee + creator fee + support`; creator's allocation before Stripe charges `B - creator fee + tip`. Never recalculate minimums on retries or the remaining amount after a partial refund. Show payment-by-payment and aggregate fees before agreement acceptance. Reject base amounts that cannot yield a valid charge/application fee; choose a publicly disclosed minimum project/installment amount before launch. | SQL bridge matches the two rates/minimums and initializes tip/support to zero. `api/server.js` checks only positive amount and application fee less than total, trusting stored fee/currency values. Draft `paymentTerms.ts` gives this rounding and per-installment rule. |
| Tips and platform support | **Defer both buyer options for launch** while leaving zero-valued ledger columns. If enabled later, default both to zero and require an explicit buyer action; tip goes to creator without Made for Stream fee, support goes to platform. Exclude both from percentage fee bases, show their destination and refund treatment, and test actual Stripe accounting. Never label a tip free of Stripe processing cost or support a donation. | Bridge inserts both as zero; payment UI shows nonzero lines, but no buyer choice or allocation workflow was found. Draft fee/refund policies describe options as if available. |
| Cancellation and delivery | Before substantive work: full refund including buyer fee and any tip/support; reverse creator fee. After work starts: stop avoidable work, retain only evidenced, usable, conforming earned value and approved non-recoverable costs within the accepted price; refund unearned prepaid base and proportional fees; cancel uncollected schedule items. Included revisions and correction of nonconforming work are distinct from a paid change order. No silence-based delivery acceptance or new charge. | `refundPolicy.ts` already drafts these rules, including two included revision rounds when unspecified, a 7-day delivery review and 14-day routine complaint window, but is marked REVIEW DRAFT. No sanctioned refund workflow updates project state. Do not imply automatic acceptance or escrow. |
| Partial milestones | Allocate earned value to the originally paid installment(s), preserve separately paid usable work/rights, calculate **cumulative** proportional refund of each installment's original buyer and creator fees with rounding at minor-unit precision, and return the remaining rounding balance on full refund. Track multiple refund IDs/amounts per charge and fee refund, not one nullable ID. Tax, tip and support treatment must be explicit on each resolution. | Draft `refundPolicy.ts` has the fee rule. Payment ledger has only `stripe_refund_id`, aggregate status and no refund amount/history; it cannot represent repeated partial refunds. |
| Silence and disputes | Waiting party sends a clear request, waits 7 calendar days, then final notice with another 7 days. Pause work and seek human review; unearned prepaid amounts remain refundable. Admin resolves against evidence and records reasons; bank disputes remain independent and time-sensitive. A dispute pauses the affected work/release and new collection until reviewed, without silently cancelling a whole project or erasing paid delivery rights. | Draft refund policy has 7+7 and evidence windows. Existing request status is submitted/accepted/declined/archived, so `archived` must not stand for cancellation or financial settlement. There is no refund/dispute cascade or admin resolution path. |

Example in CAD with a $100 base and no extras: buyer pays $105; creator is allocated $95 before Stripe charges; Made for Stream receives $10. A $40 base refund returns $42 to the buyer and reverses $2 of the creator fee. Two $10 installments each trigger the minimums, so total buyer fees are $2 and creator fees are $3. These are Made for Stream allocations, not net bank payouts.

### State effects required by that contract

| Event | Payment ledger | Schedule/project | Operational action |
| --- | --- | --- | --- |
| Checkout opened/abandoned | `requires_checkout` → `checkout_opened`; expiration may return it to a retryable state if no successful charge exists. `processing` is reserved for pending asynchronous payment. | Keep schedule `payment_required`; work remains blocked where payment is a prerequisite. | Reconcile from Stripe before creating another session. |
| Verified successful charge | `paid`; save account, session, PaymentIntent, charge, application fee, amounts and event references atomically or recoverably. | Mark the linked schedule item `paid` once, then perform its existing milestone/start/final workflow exactly once. | Reconcile Stripe and DB; never let a browser return page declare payment success. |
| Partial refund | Preserve original charge and `paid_at`; add an immutable refund/allocation row and derive `partially_refunded` from cumulative settled refunds. | Mark affected deliverable/schedule value as disputed or adjusted; freeze only the affected next step until an admin resolves it. Retain valid paid work and rights. | Record decision, fee reversal, who funded it, evidence, and notify parties. |
| Full refund or pre-work cancellation | Derive `refunded` once total refundable charge is returned; distinguish a cancelled *unpaid checkout* from a refunded *paid charge*. | Cancel outstanding installments and the unfinished agreement/work via an explicit resolution record; do not use inbox `archived` as the outcome. | Maintain the audit record and correct rights for fully refunded work. |
| Dispute opened/closed | Track dispute as a separate case over the charge, preserving paid/refunded history; derive visible `disputed` while open. On close, reconcile won/lost, amounts and prior refunds. | Put affected work/payment collection on hold pending review; close only after case outcome and earned-value decision. | Alert admin and creator immediately; capture evidence deadline and submission/outcome. |
| Creator loses charge capability | Update account state from Connect events and live Stripe verification; deny new paid sessions. | Pause new paid listing publication and outstanding collection; keep existing obligations and free listing handling distinct. | Tell creator what onboarding action is required and surface blocked projects to support. |

## Mismatches to resolve before adoption

- **Draft policies are publicly routed:** `paymentTerms.ts`, `refundPolicy.ts`, `termsOfService.ts` and `creatorTerms.ts` carry `REVIEW DRAFT` markers; Terms/refund text still has `[SUPPORT_EMAIL]` and operator placeholders. Pages render these sources through `src/pages/legal/*`. The checkout acceptance UI records these draft versions, but the API does not check acceptances before creating a Stripe session. Finalize, review, version and publish policy text before live payments; do not silently alter existing accepted versions.
- **No refund/dispute accounting:** `docs/support/payments/refunds-and-disputes.md` accurately reports that charge/fee IDs are left empty and refund/dispute events are ignored. Its statement that no fee-refund policy exists is stale relative to the 2026-09-20 **draft**, which is not adopted. Update the playbook only when the implementation and policy are approved.
- **Account freshness and Connect design:** `docs/support/payments/connect-onboarding.md` reports `account.updated` is ignored. API reads a stored readiness mirror. Existing v1 Express creation should be compared with the intended launch account configuration and liability before any migration; do not recreate an existing seller account automatically. Readiness failure must deny new checkout even if a stale listing remains visible.
- **Webhook and checkout integrity:** `api/server.js` verifies raw-body signatures and checks some session/account/amount/currency fields on success, but has no refund/dispute branches, no charge/fee persistence, and no server-side fee/policy invariant check at checkout. Reuse is based on a session and idempotency key incorporating mutable `updated_at`; concurrency and wrong-account events need tests and DB constraints. Stripe does not guarantee delivery order and may send duplicates; use durable idempotency plus current Stripe object state.
- **Manual payment confirmation:** Admin RPCs and UI actions can mark schedule payments paid outside Stripe. Restrict these before live checkout to an audited, named exception that cannot impersonate a Stripe success, or remove them. A refund must not leave a schedule falsely satisfied.
- **Policy promises ahead of features:** Draft terms describe tips, optional support, support timing, refunds, contribution returns, tax disclosure and account review. Hide/qualify unavailable options and obtain operational capacity for the promises before publication. Legal review is required for the chosen buyer countries and tax treatment.

## Ordered implementation checklist for subsequent sprints

1. **Approve launch choices and policy text.** Resolve countries/buyer eligibility, minimum installment, taxes, optional extras and final refund terms; replace placeholders; publish immutable policy versions and receipts. Align README, fee display and support playbooks.
2. **Close catalog and currency gaps.** Enforce approved country/currency/minimum at onboarding, agreement, schedule creation and API. Exempt free listings from payout readiness at DB and UI; validate free assets/links and prevent free flow from making a payment row. Ensure no paid instant download or standalone payment path opens.
3. **Lock checkout authority.** Check policy version/acceptance and agreement/schedule eligibility in the API; recompute amount, fee and recipient from authoritative rows; lock/idempotently reserve a schedule item against concurrent checkout; reject account mismatch and restricted creator accounts. Keep production API and secrets on a real server or tested Cloudflare runtime.
4. **Complete paid-event accounting.** On success fetch/verify charge and application fee on the connected account; persist IDs and allocation. Add strict identity checks, out-of-order and duplicate event handling, replay/reconciliation jobs, and an alert for stuck `processing`.
5. **Add a refund/dispute ledger and transitions.** Immutable per-charge refunds, fee refunds, dispute cases, decisions, evidence and actor/timestamp records; cumulative allocation and safe state derivation. Process Connect refund/dispute/account events, including dashboard-originated actions and pending/failed refunds. Reconcile against Stripe before and after money movement.
6. **Build human admin resolution.** Review request, earned-value breakdown, creator response, approval, idempotent Stripe refund/fee reversal, evidence deadline and audit trail. Remove/restrict manual paid confirmation. Update project holds, schedules, deliverables and rights without using `archived` as financial state.
7. **Prove launch behavior.** Meaningful server tests for signature/raw body, authorization, policy acceptance, concurrent duplicate checkouts, exact CAD fee rounding/minimums, wrong connected account, delayed/out-of-order/duplicate events, multiple partial refunds, disputes and account restriction. Run end-to-end test-mode Connect checkout, refund and dispute fixtures and compare ledger totals to Stripe before live enablement.

2. **Minimum paid installment:** choose a disclosed minimum that covers the combined minimum fees and provider costs. Recommend **CAD $5** per collected installment; current code only rejects an invalid fee-to-charge ratio.
